# iHelp — מפרט בדיקות

**קורס:** טכנולוגיות אינטרנט — להיות מהנדס Full-Stack, אוניברסיטת רייכמן, מדעי המחשב 2026
**מסמך:** 4 מתוך 11 (בדיקות, שלבי מטלה 6–7)
**תלוי ב:** `01-product-spec.md` (הכללים הנבדקים), `03-technical-design.md` (המנגנונים הנבדקים)

---

## 1. פילוסופיית הבדיקות — מה המשמעות של "זה עובד" כאן

הטענה המרכזית של iHelp אינה "הכפתורים עובדים" — אלא ש**מסד הנתונים
אוכף כל כלל שבמטריצת ההרשאות שבסעיף §9.2 של מפרט המוצר, אפילו כנגד
פונים שעוקפים לחלוטין את ה-UI**. ערכת הבדיקות מתועדפת אפוא
בהתאם (מהמטלה: "לבדוק את התהליכים המרכזיים, לא כל שורה"):

1. **הבדיקות בעלות הערך הגבוה ביותר מתקשרות עם PostgreSQL אמיתי** (Supabase מקומי) עם
   JWTs אמיתיים, ומנסות גם את הפעולה המותרת *וגם את תאומתה האסורה*.
   בדיקת הרשאות שבודקת רק את המסלול התקין אינה מוכיחה דבר; כל בדיקת RLS
   כאן מאמתת גם *מניעה* — סעיף §13.2 של המפרט הופך בדיוק את זה לקריטריון
   הצלחה.
2. **לוגיקה טהורה מקבלת בדיקות יחידה** — זולות, מהירות, ללא סביבה.
3. **ה-UI מקבל שכבה דקה**: בדיקות רינדור של רכיבים עבור אוצר מילים משותף
   ומעבר end-to-end אחד על לולאת ה-marketplace המרכזית, מפני שלולאה
   שעובדת בדפדפן היא המוצר שעובד.

מה שאינו נבדק במכוון: עיצוב, תוכן של דפים סטטיים, התנהגות תשתית
Next.js, ורכיבי ה-auth הפנימיים של Supabase עצמם — אף אחד מאלה אינו
הלוגיקה שלנו.

## 2. שכבות הבדיקה, הכלים, והיכן הן רצות

| שכבה | כלי | סביבה | קבצים |
|---|---|---|---|
| יחידה — לוגיקה טהורה | Vitest | Node, ללא DB | `lib/geo.test.ts`, `lib/validation/*.test.ts` |
| רכיב — UI משותף | Vitest + React Testing Library (jsdom) | ללא DB | `components/ui.test.tsx` |
| **אינטגרציה — RLS / RPC / מכונת מצבים** | Vitest + `@supabase/supabase-js` | **Supabase מקומי** (`npx supabase start`) | `tests/integration/*.test.ts` |
| End-to-end — לולאה מרכזית | Playwright | Supabase מקומי + `next dev` | `e2e/core-flow.spec.ts` |

בדיקות אינטגרציה ו-E2E **מדלגות אוטומטית** כאשר לא מזוהה stack מקומי
(`SUPABASE_URL` חסר), כך ש-`npm test` תמיד עובר ב-checkout ריק בעוד
הערכה המלאה רצה היכן שזה חשוב.

הערכה מסתכמת ב-**62 בדיקות Vitest** על פני 5 קבצים — 31 אינטגרציה
(מחזור חיים 11 + הרשאות 20), geo 6, סכימות validation 15, UI של רכיבים 10 —
בתוספת מפרט E2E אחד של Playwright, לכדי **63 בדיקות אוטומטיות** בסך הכול.

## 3. מה נבדק ולמה (רשימת תיוג לשלב 6 של המטלה)

### 3.1 תכונות מרכזיות ותהליכים עסקיים (אינטגרציה + E2E)

מחזור החיים המלא של הבקשה, המורץ דרך לקוחות אמיתיים כמשתמשים אמיתיים:

| # | תרחיש | מוכיח |
|---|---|---|
| F1 | משתמש מאומת יוצר בקשה דרך `create_request_with_photos` (עם תמונה שהועלתה) → סטטוס `open`, תמונות מצורפות | מסלול הכתיבה היחיד אל `help_requests` עובד ואוכף את האינווריאנטות שלו |
| F1b | משתמש מאומת יוצר בקשה **ללא תמונות** → סטטוס `open`, אפס תמונות מצורפות | התצלומים אופציונליים (0–5); מסלול הכתיבה מקבל בקשה ללא תמונה |
| F2 | משתמש מאומת שני מגיש הצעה → הבקשה עוברת ל-`has_offers` (טריגר T2) | זרימת ההצעה + סנכרון סטטוס אוטומטי |
| F3 | הבעלים קורא ל-`assign_offer` → הבקשה `assigned`, ההצעה שנבחרה `selected`, הצעת המתחרה `closed` | הרגע המכריע האטומי, כולל סגירת המתחרה |
| F4 | שני הצדדים קוראים ל-`confirm_completion` → הדגלים נקבעים לפי הפונה; הסטטוס עובר ל-`completed` רק לאחר הקריאה השנייה | סמנטיקת השלמה דו-צדדית |
| F5 | הבעלים קורא ל-`submit_rating` → שורת הדירוג קיימת, הבקשה `rated`, האגרגט של המסייע גלוי דרך `helper_ratings` | דירוג + מעבר סופי אטומי |
| F6 | הבעלים קורא ל-`cancel_request` באמצע התהליך → הבקשה `cancelled`, הצעות פעילות `closed` | פתח המילוט הסופי |
| F7 | משיכת ההצעה הפעילה האחרונה → הבקשה חוזרת ל-`open` | מחזור ה-has_offers↔open |
| F8 | הצעת `after_job`: אין מחיר מראש; לאחר השלמה דו-צדדית **המסייע שנבחר** קורא ל-`set_final_price` (זר מקבל `not_found`; `mark_paid` לפני התמחור ו-`set_final_price` שני — שניהם מקבלים `invalid_state`) | תמחור נדחה — הסכום המוסכם נקבע פעם אחת, על ידי המסייע שנבחר בלבד, לאחר ההשלמה |
| F9 | `get_helper_stats` מחזיר אגרגטים נכונים (עבודות שהושלמו, מספר וממוצע דירוגים, התפלגות כוכבים, ספירה לפי קטגוריה) עבור מסייע עם עבודה שהושלמה ודורגה; ה-view של `helper_ratings` חושף את `category` אך בחירת `rater_id`/`request_id` נכשלת (העמודות אינן קיימות ב-view) | אגרגטי המוניטין מחושבים בצד השרת ונשארים אנונימיים — הקשר קטגוריה ללא קישור למדרג/לבקשה |
| E2E | שרשרת F1–F5 המורצת דרך ה-UI האמיתי על ידי שתי הפעלות דפדפן | המוצר עובד כפי שהמשתמשים חווים אותו |

(שגיאה או תוצאה של אפס שורות — תבנית המניעה השקטה):

| # | פעולה אסורה שנוסתה | תוצאה צפויה |
|---|---|---|
| P1 | משתמש לא מאומת קורא ל-`create_request_with_photos` | `forbidden` |
| P2 | משתמש לא מאומת מכניס הצעה ישירות | מניעת insert של RLS |
| P3 | מסייע מציע על הבקשה **שלו עצמו** | מניעת insert של RLS |
| P4 | הצעה מוכנסת כשהיא נולדת `selected` | מניעת insert של RLS (נעילת סטטוס) |
| P5 | מי שאינו הבעלים קורא הצעה של מישהו אחר (הצעות אטומות) | אפס שורות |
| P6 | זר קורא בקשה `assigned` שהוא אינו צד בה | אפס שורות |
| P7 | מי שאינו הבעלים קורא ל-`assign_offer` / `cancel_request` | `not_found` (בטוח מבחינת קיום) |
| P8 | מסייע קורא ל-`submit_rating`; זר קורא ל-`confirm_completion` | `not_found` |
| P9 | הבעלים מבצע PATCH ל-`status`/`is_paid` ישירות (עדכון מלאכותי) | טריגר-שמירה `forbidden` / אפס שורות |
| P10 | משתמש מבצע PATCH ל-`is_identity_verified` / `is_admin` של עצמו | טריגר-שמירה `forbidden` |
| P11 | משתמש קורא שורת `profiles_private` של משתמש אחר (טלפון/קואורדינטות בית) | אפס שורות |
| P12 | מי שאינו צד קורא ל-`get_counterpart_contact` | `not_found`; הצדדים מצליחים רק מ-`assigned` |
| P13 | מי שאינו admin קורא ל-`review_application` / `set_request_hidden` / `revoke_verification` | `forbidden` |
| P14 | משתמש מכניס בקשה עם `status='approved'` (שורת ביקורת מזויפת) | מניעת insert של RLS |
| P15 | אנונימי (ללא JWT) קורא טבלה כלשהי / view של `helper_ratings` | מניעה / אפס שורות |

### 3.3 בדיקות מסד נתונים (אינטגרציה)

אילוצים וטריגרים כקו ההגנה האחרון:

| # | מקרה | תוצאה צפויה |
|---|---|---|
| D1 | הצעה *פעילה* שנייה של אותו מסייע על אותה בקשה | הפרת unique-index |
| D2 | בקשה שנייה מאותו סוג בעוד אחת ממתינה | הפרת partial-unique |
| D3 | הצעות הנושאות כל עמדת תמחור על אותה בקשה — הבקשות כבר אינן נושאות כוונת תשלום/התנדבות | כל שלוש העמדות (`fixed`/`volunteer`/`after_job`) מתקבלות |
| D4 | דירוג שני לאותה בקשה | הפרת PK |
| D5 | בקשה מקצועית ללא מסמך | הפרת CHECK |
| D6 | טריגר ההרשמה יוצר שורות `profiles` + `profiles_private` | שורות קיימות |
| D7 | ה-view של `helper_ratings` חושף כוכבים/הערה אך **לא** `rater_id`/`request_id` | היעדר עמודות |
| D8 | ביטול אימות זהות מנקה את שני הדגלים ומבטל בקשות מקצועיות ממתינות | הדגלים false, הבקשות `revoked` |
| D9 | הצעת `fixed` ללא מחיר / הצעת `volunteer` עם מחיר | הפרת CHECK של `price_matches_mode` |
| D10 | הצעה מוכנסת עם `final_price` שנקבע מראש (זיוף הסכום המוסכם ב-insert יעקוף את `set_final_price` וירעיל את `mark_paid`) | הפרת CHECK — נעילת insert, מיגרציה 0013 |

### 3.4 בדיקות קלט לא תקין (יחידה, סכימות zod)

כל סכימה דוחה את מה שה-DB היה דוחה — אותם גבולות, הודעה ידידותית
יותר: גבולות אורך של title/description/message, פורמטי טלפון שגויים, כוכבים
מחוץ ל-1–5, גבולות מחיר של הצעה, ספירת תמונות (מקבל 0, דוחה 6 — התצלומים אופציונליים, מקסימום 5), **מיקום
חסר (רגרסיית ה-(0,0) "Null Island")**, שדות אופציונליים חסרים
המגיעים כ-`null` (מחלקת רגרסיית ה-FormData שהתגלתה ב-review).

### 3.6 בדיקות UI בסיסיות (רכיב + E2E)

רכיב: `Stars` (רינדור אגרגט + מצב ריק), `StatusChip` (תוויות בעברית
לפי סטטוס), `Badge` (שילובי verified/professional). תצוגת מחיר
ההצעה (`OfferPriceChip`) נבדקת דרך זרימת ה-E2E, המאמתת שהסכום `₪120`
המצוטט על ידי המסייע מרונדר בעמוד הבקשה. E2E מאמתת גם שמעטפת ה-RTL
בעברית מרונדרת, שהטפסים נשלחים, ושפאנלי מחזור החיים מופיעים עבור
התפקיד הנכון במצב הנכון.

## 4. אסטרטגיית נתוני הבדיקה

בדיקות האינטגרציה הן **עצמאיות**: כל הרצה יוצרת משתמשים חד-פעמיים משלה
דרך ה-admin API של ה-stack המקומי (מותר: כלים מקומיים), מקדמת אחד
ל-admin באמצעות SQL ישיר, ובונה את ה-fixtures שלה דרך אותם RPCs
שמשתמשים היו קוראים. אין תלות ב-`scripts/seed.ts` (המשמש את הדמו, לא את
הערכה). E2E משתמשת בחשבונות הידועים של סקריפט ה-seed.

## 5. הרצה

```bash
npm test                    # unit + component (+ integration when stack is up)
npx supabase start          # local stack for integration/E2E
npm run test:e2e            # Playwright core-flow spec (starts next dev itself)
```

## 6. קריטריוני הצלחה עבור הערכה

הערכה מגשימה את סעיף §13.2 של המפרט ("כל הרשאה … מודגמת על ידי בדיקות
המנסות פעולות אסורות וצופות במניעה") כאשר כל שורה בסעיף §3.2 רצה כנגד
מסד הנתונים האמיתי ונכשלת **סגורה** (fails closed) — ושרשרת ה-F מוכיחה את
המסלול התקין מקצה לקצה.
